CREATE PROCEDURE insert_orders()
BEGIN
  DECLARE i INT DEFAULT 1;

  WHILE i <= 2000000 DO
    INSERT INTO orders (user_id, created_at)
    VALUES (
      FLOOR(1 + RAND() * 10000),  -- 10k users
      NOW() - INTERVAL FLOOR(RAND()*365) DAY
    );
    SET i = i + 1;
  END WHILE;

END$$

-- Q. Why INNER JOIN excludes unmatched data
-- ANS:  An INNER JOIN only keeps rows where the match condition is true in both tables .
-- unmatched data isn’t “ignored by accident”—it fails the condition, so it’s excluded.  
-- If you want all users, even those without orders → use LEFT JOIN
-- If you want everything from both sides, matched or not → use FULL JOIN
-- If you only want matched data → stick with INNER JOIN

-- Q2 Compare INNER JOIN vs LEFT JOIN

-- Imagine you have two tables: one with users and one with orders. When you use an INNER JOIN, the result only shows users who actually have at least one matching order. It’s like saying, “only show me people who bought something.” Anyone who didn’t place an order simply disappears from the result, as if they never existed in the users table for that query.

-- Now if you run the same scenario with a LEFT JOIN, the behavior changes. You’re now saying, “show me all users, and if they have orders, include those too.” So every user appears in the result. For users who don’t have any orders, their order-related columns will just show NULL instead of data. 
-- They’re still present—you can see them—but there’s no matching record on the orders side.   

-- Q3  Identify why joins create duplicates
-- A JOIN doesn’t “merge” rows the way we expect—it combines every matching pair.
-- So if one user has multiple matching rows in the other table, you don’t get one row—you get one row per match. 

-- Q4  Effect of joining on wrong column
-- A JOIN depends entirely on the column you use to connect the tables. If you join on the wrong column, the database will still happily combine rows—but it’s now matching based on the wrong logic.

-- Think of it like matching people using the wrong key:
-- You were supposed to match user_id to user_id
-- But you accidentally matched user_id to order_id or maybe name to name
-- Now the database starts pairing rows that were never meant to be related.
-- Two common outcomes:
-- Too many rows (data explosion)
-- If the column isn’t unique, you’ll get a lot of unintended matches.
-- Example: joining on name → every “John” matches every other “John”.
-- Wrong or missing data
-- If the columns don’t logically relate, you may get random matches or almost none at all. 

-- Q5  Why indexes improve join performance

-- When there’s no index on the join column, the database has no shortcut to find matching rows. So for every row in one table, it has to scan the entire other table to look for matches.
-- That’s like trying to find a name in a phone book by reading every single page, again and again, for each person. It works—but it’s inefficient and slow.


-- Q6  Filtering before vs after join

-- A JOIN combines rows first, and filtering (WHERE) removes rows after that. But if you filter earlier (inside a subquery or in the JOIN condition), you reduce how much data even participates in the JOIN.

-- So the difference is about when rows get eliminated:
-- Filtering before JOIN → fewer rows enter the join
-- Filtering after JOIN → more rows are joined, then removed later
